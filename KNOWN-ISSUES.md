# Known issues

This file lists what is known to be missing or wrong in the standards and the starter kit of this release, so that nothing is hidden by it. `gae-standards-v0.5` is the first release in which the standards take in what the installations have learnt: eight of the ten standards changed, and GEM and the Wave Standard are unchanged since `gae-standards-v0.1`. The starter kit's `ADOPTION.md` is at v0.12.

The items were found in two places: the reference installation, Runapp, and a second installation set up from this starter kit, in a domain where the agents' knowledge work is the delivered product. Both were set up by the framework's originator. Every finding the second installation reported upstream, those from its upgrades included, stands below, or is answered by the starter kit at v0.12 or by a standard in this release. Before this release, every candidate rule was tested and given one of four outcomes: taken into a standard, merged with another, refused with a reason, or kept here with a direction.

Each item says what is missing and the direction a fix takes. A direction is a proposal, not a rule. A rule enters a standard only through a new release, with a new version of that standard. Where a standard already carries part of a rule, the item names the standard and section and says only what is still missing. If you meet one of these in your own installation, or something not listed, report it as an issue in this repository.

## 1. Standards

### Truth Chain

- **A level has no declared scope.** The standard assumes one constitution at the top of a fixed order. An installation with two top documents of different scope, one for how the work is done and one for how the system is built, has had to say that neither stands above the other. That splits the chain in two. *Direction:* keep one order, and add a rule that a level applies only within the scope it declares and says nothing outside it. Every top document declares its scope.
- **The chain records what a statement rests on, not when.** A statement cannot be reproduced as it was read. *Direction:* every change of an entry's level and status is kept with its time; a statement carries the time its links were read; an optional validity period is set only from the source, and it governs a claim in a deliverable, not the evidence a contract rests on. The Registry Standard gets the same rule for governed values.
- **No relations between evidence entries.** Links run in one direction: implementation to contract, contract to registry and evidence, evidence to source. Truth Chain §3.2 counts corroboration only across distinct sources, but that one entry supports, contradicts or derives from another still has no form. *Direction:* a closed set of relations between entries, which a link check can read. The structure built under the Truth Chain will be called a *governed evidence graph*; the term enters with this change.
- **Confidence and evidence tier have no rule between them.** Truth Chain §3 says a link carries no more strength than its source and leaves to the instance appendix where a value's confidence stands. Nothing says whether the Registry Standard's [confidence set] and Truth Chain's [evidence tier set] may be one set, or that a value's confidence may not exceed the highest tier of the evidence it cites. *Direction:* that rule.

### Backlog, Registry, Truth Chain, GEM and Handoff: the record

- **"The file is the record" assumes the writer can write the repository.** Backlog §1 and §6, Registry §5, Truth Chain §4 and GEM §2.1 make a file or a log the record, and the tool classes that sync a database follow from it. An agent on a chat platform that reaches the repository only to read can write only a database. The starter kit lets such an installation keep the store as an append-only table and register the deviation (`ADOPTION.md` step 5); the standards have no form for it. *Direction:* let an installation declare a database table as the record, with append-only and history held by the store, and say which tool classes then do not apply and what takes their place. A row that breaks a rule stays as written and is read through a later entry that corrects it; a step agent that cannot read the store reads a verbatim export, whose hash is checked against the row before each dispatch.
- **No concept of several stores with a one-way reference rule.** An installation with one store per data owner must never name a data owner's item in its own store. GEM §2.2 and §3.1 require a retro entry to name the backlog items it concerns, and Handoff §2 puts the item in the metadata. The starter kit splits the stores (`ADOPTION.md` step 5) but cannot settle that conflict. *Direction:* let a backlog item ID, a log and a handoff store be scoped to a store, and say how the learnings function routes across stores without a reference into a data owner's store.

### Contract

- **No type for the top documents.** The closed set of document types has no type for the [constitution], which Truth Chain puts above every contract: `contract` gives it the contract section order, and `orientation` forbids rules. Nor has it a type for an installation's architecture contract, the contract that binds the standards and the instance appendix. The kit uses `contract` for both. `governance` is for the corpus's own standards, logs and process documents, and `framework` organises a set of contracts; neither says that a document binds the installation's standards and appendix and is reviewed against what is built. *Direction:* a type for each, or a rule for which type carries them.
- **The review basis for top documents is too narrow.** A full review of a constitution or an architecture contract reads the Contract Standard only. *Direction:* it also reads the Truth Chain's order and the instance appendix's intake.

### GIP and Contract: what a product does in operation

- **A model component inside a running product has no rule.** The standards govern how a product is built, not an agent that decides at run time inside it; `ADOPTION.md` step 2 only asks that the case be named. A third installation, an assistant in which a model sorts each message and words the answer while ordinary code makes every write, had to carry in its own specification what the standards do not: where the line runs between what GAE governs and what the model answers in operation; that instruction text, tool descriptions and the choice of model are governed artifacts, versioned and reviewed, not configuration; that the test questions for operation are tests, each binding a criterion of a contract, run as a gate on every change of policy data, instruction text or model; that a change of model runs the whole set; that every capability that writes data has a contract naming its permission level and whether it touches personal data, and that code makes the write after a confirmation; and that logs and statistics from operation hold the least personal data needed, without identity and with a retention period. *Direction:* a short section on model components in a product, in GIP or the Contract Standard, once an installation has built one and can measure against it.
- **No frozen measurement epoch.** A comparison between runs holds only if nothing the runs depend on was deployed between them. Only the reference installation's simulator has a rule for it. *Direction:* a run meant to be compared names its epoch, and no deploy that touches its inputs runs while the epoch is open.
- **A post that only deploys.** GIP §5.1 lets no lane skip a step, so a post that only puts changes already merged into operation runs a build loop with nothing to build. One installation has met the case once. *Direction:* a form for such a post, whose check is a real call to what was deployed (GIP §5.3, E), once a second case shows its shape.

### Security

- **No standard asks whether the product can be attacked.** The Boundary Standard governs what the agents may do, not what an attacker can do to what they build. No security failure has been measured in either installation, so no rule is built yet (GAL §9.8). *Direction:* a review role per product repository beside the tester and the verifier, with classes of attack as its checklist; a coverage ledger read from the derived inventory of what is built (GIP §6); findings marked confirmed or needing validation, in the review protocol's format and with its stop criterion (GAL §9.5); repeated runs as the method. A review of the reference installation after this release will decide the rule.

### GEM

- **An outcome is read without its conditions.** The memory standard compares outcomes, but not the conditions each arose under, so a better result can be credited to a change when the circumstances made the difference. *Direction:* a rule that an outcome is read against the conditions it arose under, and that those conditions are stored with it.
- **A gate is judged by what it stopped, not by what it let through.** GEM §6 traces a recurring pattern to its countermeasure, but not a failure found later to the gate that should have caught it. *Direction:* a failure found after a gate passed is traced to that gate, and a gate is judged by its misses as well as its stops.

### Handoff

- **The operator does not see what the next session will do.** Handoff §2 opens the handoff with the session's name and §4.1 puts the task's content in the start prompt, so the operator who carries it sees the next session's work only in the agent's working material. The second installation is trialling an operator part of six fixed lines between the metadata and the start prompt: the item, the steps, what the session does and with which tools, what it loads, what it stops for and what done looks like. *Direction,* depending on the trial: allow an operator part in the handoff's form, and a start prompt that points to one brief for the content.

### GAL

- **The agent split is not measured.** GAE divides work between agents by role. Whether a split beats one agent with modules, and how many tools an agent can hold before its choice of tool degrades, has not been measured. *Direction:* measure on fixed end-to-end cases before changing the split; merge tightly coupled agents first, and keep a split only where the merged version is measurably worse. At each change of model, try removing a rule or an agent, run the same cases, and leave it out where nothing gets worse: instructions written for a weaker model can hold a stronger one back.
- **No executor of the architect's writes.** §3 and GIP §4 have the [architect] commit task specifications and add queue posts. Where the owner rules out a write connector, the architect can specify but not write, and a coding-agent session makes the writes. *Direction:* describe an executor of the architect's writes, who counts as the change's author under §9.2 rule 5, and that the executor writes nothing the specification does not name; and say whether the decision-log entry may follow in the session that reads the executor's report (GEM §2.2 requires the same session).
- **Role names collide with agent names.** §3 names an implementation role *Planner*, a name an installation naturally gives its [architect]. The starter kit has the appendix say which role a name means (`ADOPTION.md` step 8). *Direction:* role names that cannot be mistaken for agent names, or that rule in the standard.
- **A step agent works only for a session agent.** §4.6 defines a step agent as one step of a build loop for the session agent. A specification round that the [architect] dispatches — the contract author, then the auditor, each in a fresh context — has no form, and in it no operator carries a handoff (Handoff §1.1). The starter kit holds such a round to GIP §2's rules for step agents and registers it as a deviation (`ADOPTION.md` step 4, Platform profiles). *Direction:* open the step-agent form to the specification side, with the [architect] as the agent that dispatches.
- **G2 and G3b where the agent file does not bind.** §4.2 assumes the platform loads the agent file and holds its tools. Where a session is opened with a line that only names the file, as in a desktop app with no agent picker, nothing in the file binds: G2 has no loaded core to compare, and G3b has no tool list to check. The starter kit registers that start as a departure from its own binding (`ADOPTION.md` step 8). *Direction:* say what G2 and G3b require when the agent file does not bind, and which receipt line shows it.
- **The bootstrap prompt stands outside the conformance classes.** On a chat platform the platform loads short project instructions that point to the core, so §4.3's byte-matched start template is not what loads. The starter kit versions the bootstrap with the agent and has the core compare it at start (`ADOPTION.md` step 8); the standard measures it nowhere. *Direction:* make the bootstrap prompt a component of the agent, measured by structural conformance.

## 2. Starter kit

`ADOPTION.md` v0.12 runs the setup as eight checkpoints, starts with an architecture contract and a corpus design, carries a starting backlog, the contract flow, profile A's mirror and configuration, the language default, a measurement of test growth and an upgrade step under a standing boundary rule. It checks a release on the installed paths, and lists the two rules it still gives ahead of a standard, each to be registered as a deviation (step 5, Rules ahead of the standards): the dispatched specification round in profile B, and a store kept as an append-only table. The kit has templates for profile A's bootstrap file, configuration store and mirror, and for the system overview: its data, its page and the script that renders the repository copy; the database templates are for PostgreSQL only. What follows is still missing.

- **The boundary between chat agents stands in text.** In profile A the database cannot tell one agent from another or from the owner, so a narrow write function limits what is written but not who writes it. The read connection holds the limit for an agent that only reads. *Direction to examine:* a connector per role, each with a database role that has only that role's write functions.

## 3. Scale

Everything in this release has been measured with one installation per operator and one operator. Three tracks are open. A routing step, named in three of the directions, is an agent that classifies and dispatches incoming items and does no work itself; none has been built.

- **Autonomy.** A human checkpoint could become a mechanical gate or a sample once it has never changed an outcome. No log records how often the owner approved, changed or refused, so no checkpoint can be removed on evidence. *Direction:* log every confirmation with its outcome; measure autonomy by the share of merged changes that needed no later correction, compared between changes the agents wrote and changes people wrote; let autonomy follow the class of work, set in a policy that code applies, so that an agent may start work that brings the system back in line with a contract while work that rewrites a contract waits for the owner; let a routing step propose the class, with the policy, not the step, deciding what the class permits; and test a class against the replayed decision history before it is given more room. None of this has been run.
- **Parallel sessions and several operators.** Specification agents share one working copy and run in turn. That holds for one operator and is the bottleneck for several. *Direction:* each session agent in a working copy of its own, never switching one another session may use; the set of affected contracts computed from the dependency graph before work is routed; locks per cluster of dependencies instead of per working copy; decision rights per cluster; and, with several operators, each of them an event source feeding a single routing step over one truth chain.
- **Context.** The methods already keep state outside the context window, but the standards do not state that as a principle. Implementation sessions stop at a measured context limit; specification sessions in chat rely on the model's own estimate. *Direction:* context control as a stated principle, and the two limits described as what they are. A routing step, if one is added, keeps no state of its own and reads the record at every decision.

## 4. What this release has not shown

- **Adoption by someone other than the originator.** Both installations were set up by the person who developed the framework. That a team or an outside adopter can install GAE from the starter kit alone has not been shown.
- **The whitepapers** that explain the framework stand in `whitepapers/` but are not covered by this release's checksums; each carries its own version (README, § Releases). They were revised against `gae-standards-v0.5` and published after its tag; `gae-standards-v0.5.1` changes only this sentence, so that the release bundle carries the revised papers.
- **Use of the starter kit as a whole.** Each standard was reviewed adversarially when it changed, and the v0.1 release — the headers, the release tooling and this file — in two rounds. The starter kit at v0.8, its procedure and its templates, was reviewed adversarially against the standards before release, and its database templates were tested on PostgreSQL 16; its changes in v0.9 were reviewed in two more rounds. The system overview templates added in v0.10 were tested on PostgreSQL 16 and in a browser engine and reviewed in two rounds; the live page's adapter is the platform's and was not tested. The changes to the Backlog Standard and GIP in `gae-standards-v0.4`, and the starter kit's changes in v0.11 that follow them, were reviewed in two rounds. The changes of `gae-standards-v0.5` and the starter kit's changes in v0.12 were reviewed adversarially together before release, in two rounds. The release check's commands were run on this repository's v0.2.1 tag. No installation has yet been set up from the kit from start to end, measured test growth in the form of step 4, upgraded under the standing rule as step 12 now words it, or run under the rules this release adds.
