# Known issues

This file lists what is known to be missing or wrong in the standards and the starter kit of this release, so that nothing is hidden by it. `gae-standards-v0.6` changes eight of the ten standards. GAL, GIP, Handoff, Contract and Backlog take in what the two installations met up to `gae-standards-v0.5.4`. Truth Chain gets the governed evidence graph (§3.3), and GEM a table as the record (§2.3), which Backlog, Registry, Truth Chain and Handoff point to. Boundary is as in `gae-standards-v0.5`, and the Wave Standard is unchanged since `gae-standards-v0.1`. The starter kit's `ADOPTION.md` is at v0.20, and its system overview template is new.

The items were found in two places: the reference installation, Runapp, and a second installation set up from this starter kit, in a domain where the agents' knowledge work is the delivered product. Both were set up by the framework's originator. The second installation's upstream findings were read whole, at their version 0.19, before this release. Each finding there is answered by a standard or the starter kit in this release, stands below, or was refused with a reason. Two directions were refused. One asks for a checksum path before a release exists, and every release since the first carries its checksums. The other, in `gae-standards-v0.5.4`, would give a finding drawn from several sources an evidence entry of its own; it stays in the research record and is linked to an entry per source (Truth Chain §4.1). One of the installation's local rules, carrying the register of inherited measurements on every route and not only to and from the reviewer, is not taken in, because no failure has been measured without it (GAL §9.8). Before this release, every candidate rule was tested and given one of four outcomes: taken into a standard, merged with another, refused with a reason, or kept here with a direction.

Each item says what is missing and the direction a fix takes. A direction is a proposal, not a rule. A rule enters a standard only through a new release, with a new version of that standard. Where a standard already carries part of a rule, the item names the standard and section and says only what is still missing. If you meet one of these in your own installation, or something not listed, report it as an issue in this repository.

## 1. Standards

### Backlog, GEM and Handoff: several stores

- **No concept of several stores with a one-way reference rule.** An installation with one store per data owner must never name a data owner's item in its own store. GEM §2.2 and §3.1 require a retro entry to name the backlog items it concerns, and Handoff §2 puts the item in the metadata. The starter kit splits the stores (`ADOPTION.md` step 5) but cannot settle that conflict. *Direction:* let a backlog item ID, a log and a handoff store be scoped to a store, and say how the learnings function routes across stores without a reference into a data owner's store.

### GIP and Contract: what a product does in operation

- **A model component inside a running product has no rule.** The standards govern how a product is built, not an agent that decides at run time inside it; `ADOPTION.md` step 2 only asks that the case be named. A third installation, an assistant in which a model sorts each message and words the answer while ordinary code makes every write, had to carry in its own specification what the standards do not: where the line runs between what GAE governs and what the model answers in operation; that instruction text, tool descriptions and the choice of model are governed artifacts, versioned and reviewed, not configuration; that the test questions for operation are tests, each binding a criterion of a contract, run as a gate on every change of policy data, instruction text or model; that a change of model runs the whole set; that every capability that writes data has a contract naming its permission level and whether it touches personal data, and that code makes the write after a confirmation; and that logs and statistics from operation hold the least personal data needed, without identity and with a retention period. *Direction:* a short section on model components in a product, in GIP or the Contract Standard, once an installation has built one and can measure against it.
- **No frozen measurement epoch.** A comparison between runs holds only if nothing the runs depend on was deployed between them. Only the reference installation's simulator has a rule for it. *Direction:* a run meant to be compared names its epoch, and no deploy that touches its inputs runs while the epoch is open.
- **A post that only deploys.** GIP §5.1 lets no lane skip a step, so a post that only puts changes already merged into operation runs a build loop with nothing to build. One installation has met the case once. *Direction:* a form for such a post, whose check is a real call to what was deployed (GIP §5.3, E), once a second case shows its shape.

### Registry

- **A governed value does not say when its evidence was read.** Truth Chain §3.3 has a statement carry the time its links were read, so that it can be reproduced as it was read. The Registry Standard has no such field for a value: §2.2 names the evidence that bears it, not when that evidence was last read for it. *Direction:* the Registry Standard gets the same rule for governed values, with the field bound in the instance appendix.

### Security and Boundary

- **No standard asks whether the product can be attacked.** The Boundary Standard governs what the agents may do, not what an attacker can do to what they build. No security failure has been measured in either installation, so no rule is built yet (GAL §9.8). *Direction:* a review role per product repository beside the tester and the verifier, with classes of attack as its checklist; a coverage ledger read from the derived inventory of what is built (GIP §6); findings marked confirmed or needing validation, in the review protocol's format and with its stop criterion (GAL §9.5); repeated runs as the method. For the agents' own infrastructure, the same review asks whether each agent or role has an identity of its own, and whether the agents' turns are logged. A review of the reference installation will decide the rule.
- **A store's rules stand in the agent's instructions.** An agent reaches a store through generic database access, and the rules of what it may write stand in its instructions. *Direction:* a server for the domain that carries the rules of the installation's truth layer: writes only through predefined actions with their conditions, and changing a type kept apart from writing data. Not yet built in either installation.

### GEM

- **An outcome is read without its conditions.** The memory standard compares outcomes, but not the conditions each arose under, so a better result can be credited to a change when the circumstances made the difference. *Direction:* a rule that an outcome is read against the conditions it arose under, and that those conditions are stored with it.
- **Whether a learning changed anything cannot be measured.** GEM §7 records that a learning was read, but the read count overwrites the first read, every pattern began to be read at the same time, and the retro log counts that a pattern's name is used, not that its failure occurs. *Direction:* each read kept as an event, with the first read kept; the effect measured on outcomes the agent does not name itself (review findings, failed gates, rework), compared with sessions that did not get the learning. The second installation already keeps reads as events. The rule follows once a comparison has run.
- **A gate is judged by what it stopped, not by what it let through.** GEM §6 traces a recurring pattern to its countermeasure, but not a failure found later to the gate that should have caught it. *Direction:* a failure found after a gate passed is traced to that gate, and a gate is judged by its misses as well as its stops. This is the measure of the governed ablation item below.

### Handoff

- **The operator does not see what the next session will do.** Handoff §2 opens the handoff with the session's name and §4.1 puts the task's content in the start prompt, so the operator who carries it sees the next session's work only in the agent's working material. The second installation carries an operator part of six fixed lines between the metadata and the start prompt in every handoff: the item, the steps, what the session does and with which tools, what it loads, what it stops for and what done looks like. *Direction,* once the installation has written the outcome of that trial: allow an operator part in the handoff's form, and a start prompt that points to one brief for the content.
- **A question to an owner can disappear.** A question an agent puts to an owner has no state, so an unanswered one can be dropped without a trace, and a criterion reported done carries no pointer to the check that bears it. *Direction:* a question is an item with a status (open, answered, written off with a reason) that travels with the handoff, and every criterion reported done names its check.

### GAL

- **The agent split is not measured.** GAE divides work between agents by role. Whether a split beats one agent with modules, and how many tools an agent can hold before its choice of tool degrades, has not been measured. *Direction:* measure on fixed end-to-end cases before changing the split, with the method of the governed ablation item below; merge tightly coupled agents first, and keep a split only where the merged version is measurably worse. Where the owner checks the work between two agents, the split also follows from that check, and a check removed on evidence is the moment to test a merge.
- **Governed ablation: no rule may be removed on evidence.** The standards grow by rules written against measured failures, but nothing tests whether a rule still earns its place. GAL §4.7.3 p. 3 removes a check that stopped nothing in 30 days, which a rule against a rare failure fails by design. *Direction:* a fixed regression suite for the governance, drawn from real failures and seeded with planted rare ones, with a control group of cases where nothing is wrong and a sealed part opened once; each run reported per case as pass^k against a stored baseline, outcome before path, with cost per case; each removal a pre-registered hypothesis that the owner decides. A path rule (a mandatory block, a fixed step) keeps its right to stop only where it serves a named rule: safety, an owner decision, a budget or a promise. At each change of model the suite runs again, since instructions written for a weaker model can hold a stronger one back. Replaying past sessions with their tool results frozen is the way to test a change against history. None of this has been run.
- **A new block is not observed before it blocks.** A new gate starts by stopping work, so its false alarms are found by the work it stops. *Direction:* a new block runs first in an observing mode that logs what it would have stopped, and blocks only once its alarms have been read. Boundary's rule of no standing way around a block stays.
- **No executor of the architect's writes.** §3 and GIP §4 have the [architect] commit task specifications and add queue posts. Where the owner rules out a write connector, the architect can specify but not write, and a coding-agent session makes the writes. *Direction:* describe an executor of the architect's writes, who counts as the change's author under §9.2 rule 5, and that the executor writes nothing the specification does not name; and say whether the decision-log entry may follow in the session that reads the executor's report (GEM §2.2 requires the same session).
- **A step agent works only for a session agent.** §4.6 defines a step agent as one step of a build loop for the session agent. A specification round that the [architect] dispatches — the contract author, then the auditor, each in a fresh context — has no form, and in it no operator carries a handoff (Handoff §1.1). The starter kit holds such a round to GIP §2's rules for step agents and registers it as a deviation (`ADOPTION.md` step 4, Platform profiles). *Direction:* open the step-agent form to the specification side, with the [architect] as the agent that dispatches.
- **The bootstrap prompt stands outside the conformance classes.** On a chat platform the platform loads short project instructions that point to the core, so §4.3's byte-matched start template is not what loads. The starter kit versions the bootstrap with the agent and has the core compare it at start (`ADOPTION.md` step 8); the standard measures it nowhere. No failure has been measured where the two differed. *Direction:* make the bootstrap prompt a component of the agent, measured by structural conformance, once one is.

### Convergence: an order of several parts

`gae-standards-v0.5.3` closed the three routes by which one order kept growing, and this release holds an item's current state apart from its history (Backlog §2.3), reads "in full" as the rule and not the file (GAL §4.7.1), and attests a change part by part (GAL §9.3). What follows is what is still open.

- **Nothing reports an order that does not shrink.** An order that is split again and again is still seen only by someone who reads the decision log. *Direction:* a sensor (GAL §4.2, GEM) that reports to the owner when an order has been split more than a set number of times, or when a part's remainder is not smaller than its parent by a set share.
- **No limit on what an order bundles.** The order in the case carried more than thirty riders, and the rule that siblings are changed together made its parts large and serial. *Direction:* a limit on what one order may bundle, and the sibling rule held to what the order itself changes.
- **The reading budget is not measured.** A session split its work on a reading budget inherited from a retro entry and never measured. *Direction:* the reading budget as a calibration in the instance appendix, measured by a stated method, and work split at the measured context limit.

## 2. Starter kit

`ADOPTION.md` v0.20 runs the setup as eight checkpoints, starts with an architecture contract and a corpus design, carries a starting backlog, the contract flow, profile A's mirror and configuration, the language default, a measurement of test growth and an upgrade step under a standing boundary rule. A description of the system shortens the intake and is no longer required. It checks a release on the installed paths, and gives one rule ahead of a standard, to be registered as a deviation (step 5, Rules ahead of the standards): the dispatched specification round in profile B. The kit has templates for profile A's bootstrap file, configuration store and mirror, and for the system overview: its data, its page and the script that renders the repository copy; the database templates are for PostgreSQL only. The overview page embeds three fonts under the SIL Open Font License 1.1, whose notices and text stand in its header; the rest of the page is MIT. What follows is still missing.

- **The boundary between chat agents stands in text.** In profile A the database cannot tell one agent from another or from the owner, so a narrow write function limits what is written but not who writes it. The read connection holds the limit for an agent that only reads. *Direction to examine:* a connector per role, each with a database role that has only that role's write functions.

## 3. Scale

Everything in this release has been measured with one installation per operator and one operator. Three tracks are open. A routing step, named in three of the directions, is an agent that classifies and dispatches incoming items and does no work itself; none has been built.

- **Autonomy.** A human checkpoint could become a mechanical gate or a sample once it has never changed an outcome. No log records how often the owner approved, changed or refused, so no checkpoint can be removed on evidence. *Direction:* keep every approval, change, refusal and correction by the owner as an event — what was proposed, what was chosen and what was not, and a line of why in the owner's words — and turn a correction that recurs into a contract rule through the ordinary process, never by itself; measure autonomy by the share of merged changes that needed no later correction, compared between changes the agents wrote and changes people wrote; let autonomy follow the class of work, set in a policy that code applies, so that an agent may start work that brings the system back in line with a contract while work that rewrites a contract waits for the owner; give a flow that will act with consequences three steps, a shadow mode that writes what it would do, a named sample, and full volume, each with a criterion written before the run and a step back when it fails; let a trigger for deferred work be an event or a timer, not a sentence; let a routing step propose the class, with the policy, not the step, deciding what the class permits; and test a class against the replayed decision history before it is given more room. None of this has been run.
- **Parallel sessions and several operators.** Specification agents share one working copy and run in turn. That holds for one operator and is the bottleneck for several. *Direction:* each session agent in a working copy of its own, never switching one another session may use; an owner per contract and per domain, named in the contract, to whom an agent's question about a requirement goes through the dependency graph; the set of affected contracts and owners computed from that graph before work is routed, with the owner of what changes deciding and the owners of what depends on it able to stop a change that breaks their boundary; locks per cluster of dependencies instead of per working copy; and, with several operators, each of them an event source feeding a single routing step over one truth chain. Counting only changes to what a contract promises outward needs a contract that keeps its promise apart from its inside, which no standard yet asks.
- **Context.** The methods already keep state outside the context window, but the standards do not state that as a principle. Implementation sessions stop at a measured context limit; specification sessions in chat rely on the model's own estimate. *Direction:* context control as a stated principle, and the two limits described as what they are. A routing step, if one is added, keeps no state of its own and reads the record at every decision.

## 4. What this release has not shown

- **Adoption by someone other than the originator.** Both installations were set up by the person who developed the framework. That a team or an outside adopter can install GAE from the starter kit alone has not been shown.
- **The whitepapers** that explain the framework stand in `whitepapers/` but are not covered by this release's checksums; each carries its own version (README, § Releases).
- **The rules this release adds, in use.** No installation has yet run a start under GAL's one-route form or its stops for the architect's start option, kept a table as the record under GEM §2.3 rather than as a registered deviation, kept an evidence graph to Truth Chain §3.3 and measured its searches' counts, or named its own mutation probe kinds under GIP's C.5. The second installation's graph, its record tables and its search were read before the text was written, and its search leaves out nodes not yet indexed without counting them, which §3.3 now asks it to count. Nor has any installation yet closed a change with a reading round under GAL §9.7 p. 3, had a merged diff read for its architect under GIP §6, been set up from the kit from start to end, measured test growth in the form of step 4, or upgraded under the standing rule as step 12 words it.
- **Use of the starter kit as a whole.** Each standard was reviewed adversarially when it changed. The changes in this release were reviewed in two adversarial rounds. The second ended with two blocking findings, which the owner closed at the round limit: the fixes were checked against the reviewer's own tests, not reviewed in a third round. Seventeen places where a rule now lets through what it stopped before were decided by the owner as intended before the review, each with how far it may go. The system overview template of this release was rendered in one browser engine, light and dark, desktop and mobile, on an invented document; its data and its render script are unchanged, and the live page's adapter is the platform's and was not tested.
