# Known issues

This file lists what is known to be missing or wrong in the standards and the starter kit of this release, so that nothing is hidden by it. The standards are unchanged since `gae-standards-v0.1`; the starter kit's `ADOPTION.md` is at v0.9.

The items were found in two places: the reference installation, Runapp, and a second installation set up from this starter kit, in a domain where the agents' knowledge work is the delivered product. Both were set up by the framework's originator. Every finding the second installation reported upstream, those from its upgrades included, stands below, or is answered by the starter kit at v0.9.

Each item says what is missing and the direction a fix takes. A direction is a proposal, not a rule. A rule enters a standard only through a new release, with a new version of that standard. Where a standard already carries part of a rule, the item names the standard and section and says only what is still missing. If you meet one of these in your own installation, or something not listed, report it as an issue in this repository.

## 1. Standards

### Truth Chain

- **A level has no declared scope.** The standard assumes one constitution at the top of a fixed order. An installation with two top documents of different scope, one for how the work is done and one for how the system is built, has had to say that neither stands above the other. That splits the chain in two. *Direction:* keep one order, and add a rule that a level applies only within the scope it declares and says nothing outside it. Every top document declares its scope.
- **The chain records what a statement rests on, not when.** A statement cannot be reproduced as it was read. *Direction:* every change of an entry's level and status is kept with its time; a statement carries the time its links were read; an optional validity period is set only from the source. The Registry Standard gets the same rule for governed values.
- **No relations between evidence entries.** Links run in one direction: implementation to contract, contract to registry and evidence, evidence to source. That one entry supports, contradicts or derives from another has no form. So two entries that appear to corroborate each other while resting on one study cannot be told apart. *Direction:* a closed set of relations between entries, and a rule that corroboration counts only across distinct sources. The structure built under the Truth Chain will be called a *governed evidence graph*; the term enters with this change.
- **[implementation] is defined as code.** Truth Chain §1.1 and Registry §1.1 both define [implementation] as the code that executes the contracts under GIP, and Truth Chain §2.1 puts it at level 3. Where the agents' knowledge work is the product, that level holds the agents' deliverables. The starter kit binds [implementation] to them (`ADOPTION.md` step 3); neither standard has a definition that allows it. Bound so, Truth Chain §2.3 forbids a deliverable produced before its contract, which the starter kit allows when the deliverable is marked *before contract* (`ADOPTION.md` step 10). *Direction:* name the knowledge corpus as a supported shape, and let Truth Chain and Registry bind [implementation] to agent-made deliverables, separately from GIP's product, with a rule for a deliverable produced before its contract.
- **Confidence and evidence tier have no rule between them.** Truth Chain §3 says a link carries no more strength than its source and leaves to the instance appendix where a value's confidence stands. Nothing says whether the Registry Standard's [confidence set] and Truth Chain's [evidence tier set] may be one set, or that a value's confidence may not exceed the highest tier of the evidence it cites. *Direction:* that rule.

### Backlog, Registry, Truth Chain, GEM and Handoff: the record

- **"The file is the record" assumes the writer can write the repository.** Backlog §1 and §6, Registry §5, Truth Chain §4 and GEM §2.1 make a file or a log the record, and the tool classes that sync a database follow from it. An agent on a chat platform that reaches the repository only to read can write only a database. The starter kit lets such an installation keep the store as an append-only table and register the deviation (`ADOPTION.md` step 5); the standards have no form for it. *Direction:* let an installation declare a database table as the record, with append-only and history held by the store, and say which tool classes then do not apply and what takes their place.
- **No concept of several stores with a one-way reference rule.** An installation with one store per data owner must never name a data owner's item in its own store. GEM §2.2 and §3.1 require a retro entry to name the backlog items it concerns, and Handoff §2 puts the item in the metadata. The starter kit splits the stores (`ADOPTION.md` step 5) but cannot settle that conflict. *Direction:* let a backlog item ID, a log and a handoff store be scoped to a store, and say how the learnings function routes across stores without a reference into a data owner's store.

### Contract

- **No type for the top documents.** The closed set of document types has no type for the [constitution], which Truth Chain puts above every contract: `contract` gives it the contract section order, and `orientation` forbids rules. Nor has it a type for an installation's architecture contract, the contract that binds the standards and the instance appendix. The kit uses `contract` for both. `governance` is for the corpus's own standards, logs and process documents, and `framework` organises a set of contracts; neither says that a document binds the installation's standards and appendix and is reviewed against what is built. *Direction:* a type for each, or a rule for which type carries them.
- **An empty implementation scope is allowed.** A contract whose rules govern something built may leave its implementation scope empty, and a completeness check then has nothing to count. *Direction:* such a contract names its implementation, or states why it does not.
- **The auditor may not be able to write `last_audit`.** Contract §8.4 has the auditor write it right after its verdict. An auditor on a chat platform that reaches the repository only to read can write its report but not the file it audited. The starter kit binds another writer in the instance appendix (`ADOPTION.md` step 11); the standard does not allow it. *Direction:* let the agent that commits the audited document write `last_audit` from the auditor's report, with the version the auditor read, when the auditor cannot write the document's store.
- **A prohibition must stand apart from its rule.** §4.3 fixes a section order with Prohibited Behavior and Failure Modes, and §4.1 lets a section that does not apply be omitted. It does not say whether the two sections apply to a contract whose rules are grouped by principle, each with the prohibitions that bound it, so such a contract moves every prohibition away from the rule it qualifies. *Direction:* say that a prohibition may stand with the rule it belongs to, one rule per item (§4.9), and that the two sections then count as not applying under §4.1.
- **A reference must use the full title.** §4.10 requires a reference by full title, and §4.8 prohibits an implicit one. Where every document's file name is a slug that is unique in the corpus and is the index's key, the slug already names one document, and a full title breaks when the title changes. *Direction:* allow a reference by a unique, indexed key as an explicit reference.
- **No place for wording that must keep its own language.** §7.3 permits no mixed-language text in a body except metadata values, quoted identifiers and comments in code blocks. A contract that records a client's decisions must sometimes carry the client's or a source's own wording, which translated is no longer that wording. The starter kit marks such wording as a quotation, `"…" [xx]` (`ADOPTION.md` step 4); the standard does not allow it. *Direction:* add the marked quotation, read as data and never as a rule, to the exemptions of §7.3.
- **The review basis for top documents is too narrow.** A full review of a constitution or an architecture contract reads the Contract Standard only. *Direction:* it also reads the Truth Chain's order and the instance appendix's intake.

### GEM

- **An outcome is read without its conditions.** The memory standard compares outcomes, but not the conditions each arose under, so a better result can be credited to a change when the circumstances made the difference. *Direction:* a rule that an outcome is read against the conditions it arose under, and that those conditions are stored with it.

### Handoff and Boundary

- **Carrying a handoff is not separated from deciding on it.** The standards assume the operator carries every handoff from one session to the next (Handoff §1.1, [operator]). A coding-agent platform can let one agent open the next agent's session with the handoff as its first message; the operator then confirms the decision in the new session but no longer carries the text. The standards do not say which of the two is the operator's role. *Direction:* transport and decision are separate in the Handoff and Boundary standards, and the decision stays with the operator.
- **`Last commit` assumes the giver commits.** Handoff §2 and GAL §4.2 G3 read the last commit the giver made. An agent whose writes are database rows has none. *Direction:* generalise it to the giver's last durable write, in a form the receiver can read back.
- **The receiver's starting point is not in the handoff's metadata.** The metadata carries the giver's last commit, but not the commit and branch the receiver should find, so the operator cannot compare it with the receiver's start receipt. *Direction:* the metadata carries both.
- **A handoff received in the middle of a session.** GAL §4.2 runs the gates once, at session start, and §6.1 reads the `Handoff:` line from the first message. Handoff §6 has the receiver check the target and the premises whenever a handoff reaches it, but nothing says whether a handoff pasted into a session that is already running gets a new receipt. The handoff names a state the session has not seen: its `Last commit`, and the modules it loads. *Direction:* a handoff received mid-session runs G1, G3 and G4 again and emits those receipt lines before any work on it.
- **The operator does not see what the next session will do.** Handoff §2 opens the handoff with the session's name and §4.1 puts the task's content in the start prompt, so the operator who carries it sees the next session's work only in the agent's working material. The second installation is trialling an operator part of six fixed lines between the metadata and the start prompt: the item, the steps, what the session does and with which tools, what it loads, what it stops for and what done looks like. *Direction,* depending on the trial: allow an operator part in the handoff's form, and a start prompt that points to one brief for the content.

### Backlog

- **Every finding becomes an item, an advisory one too.** §4.1 routes every finding to an open item, a reopened item or a new ID, and under §4.2 a finding routed to an item that does not exist is not disposed of. A review whose findings are mostly advisory then opens items only the next change of the same file can close. The starter kit routes an advisory finding to the item that next changes the same surface (`ADOPTION.md` step 4); the standard does not allow it where no such item is open. *Direction:* let an installation route the advisory class to the next change of the same surface, carried there under §4.2.

### GIP

- **A product is a repository.** §1 and §3 speak of a product repository with its own write gate. Where the schema and templates share a repository with governance, the product is a set of path prefixes. *Direction:* allow a product to be declared as paths in a repository, with the write gate and the merge check working by path.
- **No bootstrap path for the first post.** §3 forbids code on main without a queue post that passed its gate, and §5.1 a build loop without a runnable suite. When the first post builds the queue and the suite, no post can pass. The starter kit registers a deviation for that one post (`ADOPTION.md` step 10); the standard has no rule. *Direction:* a bootstrap rule for the first post, which records the first queue and suite outside the pipeline and brings them in afterwards.
- **A hard stop has no way to close with open findings.** At the review-round limit without a pass, §5.1 and §8 let the owner choose only whether the post continues, is split or goes back to dispatch, and the merge is not the owner's. A post whose remaining findings the owner would carry in a backlog item has no form. The starter kit lets the owner close with the open findings carried (`ADOPTION.md` step 4); the standard does not. *Direction:* name that choice among the owner's at a hard stop, with what a carried finding must say.

### GAL

- **How an agent puts a decision to the owner is only partly covered.** GAL §9.3 (Approved-change list governance, p. 3) requires that an attestation carries its material and one yes/no question. Nothing in GAL requires that a decision question states what a yes will lead to. The starter kit's procedure and its core template carry the rule; the standard does not. *Direction:* the requirement in GAL.
- **The agent split is not measured.** GAE divides work between agents by role. Whether a split beats one agent with modules, and how many tools an agent can hold before its choice of tool degrades, has not been measured. *Direction:* measure on fixed end-to-end cases before changing the split; merge tightly coupled agents first, and keep a split only where the merged version is measurably worse.
- **G2 can compare two copies of one stale state.** §4.2 G2 compares the version registry with the loaded core. Where both come through one periodic sync, G2 always passes, and its mismatch response, reading the core from the repository, has no route. The starter kit has profile A read from a mirror and applies G2 against it (`ADOPTION.md` step 4). *Direction:* G2's two sides come from independent routes, and G2 halts where no route to the current core exists.
- **G3 assumes the remote main.** §4.2 has G3 bring the working tree to the remote main, in the session agent's form and in the form for a specification agent on the coding-agent platform. A reviewer or a session agent that works on a branch across sessions then gets a warning at every start and leaves main outside the gate. *Direction:* G3 brings the working tree to the branch the handoff names, and to main when it names none.
- **One Auto-Retro text for every agent kind.** §4.4 holds one core text that says where the retro entry is appended. A session agent's entry is carried in its report and entered by the [architect], so the shared text tells it to do what its close forbids. *Direction:* the Auto-Retro core text is held per agent kind.
- **No executor of the architect's writes.** §3 and GIP §4 have the [architect] commit task specifications and add queue posts. Where the owner rules out a write connector, the architect can specify but not write, and a coding-agent session makes the writes. *Direction:* describe an executor of the architect's writes, who counts as the change's author under §9.2 rule 5, and that the executor writes nothing the specification does not name; and say whether the decision-log entry may follow in the session that reads the executor's report (GEM §2.2 requires the same session).
- **Role names collide with agent names.** §3 names an implementation role *Planner*, a name an installation naturally gives its [architect]. The starter kit has the appendix say which role a name means (`ADOPTION.md` step 8). *Direction:* role names that cannot be mistaken for agent names, or that rule in the standard.
- **An approval lapses with any later change.** §9.2 rule 3 lets an attestation lapse when any of its inputs changes, so a change that only fixes the findings an approving round named needs a new round. The Contract Standard does the same for an audit: a record of an earlier version is no basis for promotion (Contract §8.2), and the full audit is on the current version (§8.4). The starter kit lets a `yes` hold over such fixes, and corrects a factual error found after approval in one bounded round over the changed places only (`ADOPTION.md` step 4); the standards do not. *Direction:* say which later changes an approval holds over, and what the reviewer must still read of them.
- **Every change gets the full adversarial round.** §9.5 runs once per agent a change touches, over the whole pre-state and post-state, and passes only with no rule weakened or lost. A change that only rewords, adding or removing no rule, costs a full round, and a change cannot close at a round limit with findings still open. The starter kit gives a rewording one reading round, and lets the owner close at the round limit with the open findings carried (`ADOPTION.md` step 4); the standard does neither. *Direction:* define a reading round for such a change, and say what it must still measure; say whether, and how, a change closes with findings carried.
- **A step agent works only for a session agent.** §4.6 defines a step agent as one step of a build loop for the session agent. A specification round that the [architect] dispatches — the contract author, then the auditor, each in a fresh context — has no form, and in it no operator carries a handoff (Handoff §1.1). The starter kit holds such a round to GIP §2's rules for step agents and registers it as a deviation (`ADOPTION.md` step 4, Platform profiles). *Direction:* open the step-agent form to the specification side, with the [architect] as the agent that dispatches.
- **The bootstrap prompt stands outside the conformance classes.** On a chat platform the platform loads short project instructions that point to the core, so §4.3's byte-matched start template is not what loads. The starter kit versions the bootstrap with the agent and has the core compare it at start (`ADOPTION.md` step 8, `Bootstrap: current`); the standard measures it nowhere. *Direction:* make the bootstrap prompt a component of the agent, measured by structural conformance.

## 2. Starter kit

`ADOPTION.md` v0.9 runs the setup as eight checkpoints, starts with an architecture contract and a corpus design, carries a starting backlog, the contract flow, profile A's mirror and configuration, the language default, a measurement of test growth and an upgrade step under a standing boundary rule. It checks a release on the installed paths, and lists every rule it gives ahead of a standard, each to be registered as a deviation (step 5, Rules ahead of the standards). The kit has templates for profile A's bootstrap file, configuration store and mirror; the database templates are for PostgreSQL only. What follows is still missing.

- **No template for the system overview.** Step 8 says what the overview shows, that it reads a view through a read-only connection and that the checkpoints' status is computed. The page is drawn by each installation; a template with fixed sections, design tokens and a data format, rendered by a script so that an agent fills data and never layout, has been designed and tried but is not in the kit.
- **The boundary between chat agents stands in text.** In profile A the database cannot tell one agent from another or from the owner, so a narrow write function limits what is written but not who writes it. The read connection holds the limit for an agent that only reads. *Direction to examine:* a connector per role, each with a database role that has only that role's write functions.

## 3. Scale

Everything in this release has been measured with one installation per operator and one operator. Three tracks are open.

- **Autonomy.** A human checkpoint could become a mechanical gate or a sample once it has never changed an outcome. No log records how often the owner approved, changed or refused, so no checkpoint can be removed on evidence. *Direction:* log every confirmation with its outcome.
- **Parallel sessions and several operators.** Specification agents share one working copy and run in turn. That holds for one operator and is the bottleneck for several. *Direction:* the set of affected contracts computed from the dependency graph before work is routed; locks per cluster of dependencies instead of per working copy; decision rights per cluster.
- **Context.** The methods already keep state outside the context window, but the standards do not state that as a principle. Implementation sessions stop at a measured context limit; specification sessions in chat rely on the model's own estimate. *Direction:* context control as a stated principle, and the two limits described as what they are.

## 4. What this release has not shown

- **Adoption by someone other than the originator.** Both installations were set up by the person who developed the framework. That a team or an outside adopter can install GAE from the starter kit alone has not been shown.
- **The whitepapers** that explain the framework are not part of this release.
- **Use of the starter kit as a whole.** Each standard was reviewed adversarially when it changed, and the v0.1 release — the headers, the release tooling and this file — in two rounds. The starter kit at v0.8, its procedure and its templates, was reviewed adversarially against the standards before release, and its database templates were tested on PostgreSQL 16; its changes in v0.9 were reviewed in two more rounds. The release check's commands were run on this repository's v0.2.1 tag. No installation has yet been set up from the kit from start to end, measured test growth in the form of step 4, or upgraded under the standing rule as step 12 now words it.
